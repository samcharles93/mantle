# CL 864041 — VEX encodings for AVX-VNNI VPDP instructions

    https://go-review.googlesource.com/c/go/+/864041     NEW, master, +26/-4

## What it changes

`src/cmd/internal/obj/x86/avx_optabs.go` (+12/-4): adds the 128- and 256-bit VEX
rows for `VPDPBUSD`, `VPDPBUSDS`, `VPDPWSSD`, `VPDPWSSDS`, and switches those four
mnemonics from the EVEX-only `_yvblendmpd` operand template to `_yvandnpd`, which
covers VEX and EVEX.

`src/cmd/asm/internal/asm/testdata/amd64enc_extra.s` (+13): twelve hand-added
encoder cases covering both vector widths, the R/X/B extension registers and a
memory operand.

This is the assembler half of Sam's earlier CL 745780, split out because Cherry Mui
asked for exactly that on 2026-02-17: "Could you put the assembler change to a
separate CL? We can review and land that part on the main branch." The archsimd
`AddDotProductQuads` half stays behind because he also asked for new SIMD APIs to
develop on `dev.simd`, with the VPDPB family designed together in #73787.

## Why the table is edited directly rather than regenerated

`avx_optabs.go` is generated by `x86avxgen` (in x/arch) from Intel XED datafiles.
Two facts, both verified here:

1. **x86avxgen cannot consume current Intel XED.** Built `intelxed/xed` master
   (`0bcb6237`, v2026.08.23) per the xeddata doc, with `mbuild` as its sibling, and
   `./mfile.py` produces `obj/dgen/*.txt`. Feeding that to `x86avxgen -xedPath`
   dies on AMX tile forms:

       "Iform": "TDPBF16PS_TMMf32_TMM2bf16_TMM2bf16"
       }: args[0]: unexpected TMM_R() reg

2. **The XED data the generator *is* tested against lacks the VEX forms for these
   four mnemonics.** `x86/x86avxgen/testdata/xedpath/all-dec-instructions.txt`
   contains 222 `VV1` (VEX) objects and 3023 `EVV` (EVEX) objects, so VEX generation
   works in general, but every `ICLASS: VPDPB*` object in it has `PATTERN: EVV`.
   That is why the generated table only has `evex*` rows and `_yvblendmpd`.

To confirm the table edit is what the generator would produce given the data, the
real VEX objects were extracted from the XED build (64 objects, `PATTERN: VV1`,
`EXTENSION: AVX_VNNI`) into a scratch copy of the fixture, and the generator run
against it. It emits, for `VPDPBUSD`:

    {as: AVPDPBUSD, ytab: _yvandnpd, prefix: Pavx, op: opBytes{
        avxEscape | vex128 | vex66 | vex0F38 | vexW0, 0x50,
        avxEscape | vex256 | vex66 | vex0F38 | vexW0, 0x50,
        avxEscape | evex128 | ... 0x50,
        ...

which is byte-identical to the hand edit in this CL. `generator-vs-manual.diff` in
this directory records the comparison (the remaining diff is unrelated drift between
the pinned fixture and today's x/arch master).

## Verification

Toolchain built from the patched tree (`src/make.bash`, bootstrap Go 1.27.4):

    go test cmd/asm/... cmd/internal/obj/x86     # all pass

Encoding, from `go tool objdump` on the patched toolchain:

    VPDPBUSD Y1, Y0, Y2   -> c4e27d50d1     (VEX c4, not EVEX 62)
    VPDPBUSD X0, X1, X2   -> c4e27150d0
    VPDPBUSD X12, X13, X14 -> c4421150f4    (R and B extension bits)

Executed on this CPU (Alder Lake, AVX-VNNI, no AVX-512) from a `.s` file:
`dot_amd64.s` computes a 32-byte u8 x i8 dot product with one `VPDPBUSD Y1, Y0, Y2`
and returns eight int32 lanes. `main.go` checks it against a scalar reference:

    lanes: [20 148 404 788 1300 1940 2708 3604]
    want:  [20 148 404 788 1300 1940 2708 3604]
    MATCH: true

`enc_amd64.s` is the scratch file the twelve encodings were read from.

# Companion CL 863322 — x86avxgen skips unmodelled operands

    https://go-review.googlesource.com/c/arch/+/863322    NEW, master, +46/-7

`x86/x86avxgen/decode.go`: an XED operand class or broadcast tuple the generator
does not model was a fatal error, so the tool died on the first unknown thing in a
current Intel XED. It now records the object as skipped, accumulates the reason, and
reports the totals at the end of `DecodeAll`.

Against Intel XED v2026.08.23 (`0bcb6237`) the decode stage completes:

    6237 instructions decoded, 2188 XED objects skipped, reasons reported:
      GPRv_N() x556, GPRv_B() x428, GPRv_R() x384, GPR8_B() x193, GPR8_N() x170,
      GPR8_R() x101, GPR64_N() x56, GPR32_N() x56, TMM_R3() x19, TMM_R() x18,
      TMM_B3() x12, IMM0 width z x120, IMM0 width d x8, XED_REG_CL x42,
      XED_REG_BSR0 x11, plus 18 EVEX broadcast tuples over NELEM_QUARTER()

Most of that is APX and AMX, i.e. ISA extensions Go's assembler has no operand types
for. The APX list is worth reading twice: `GPRv_*`/`GPR8_*` are largely *renames* of
classes the map already knows under other spellings, so a chunk of those 2188 could
be recovered by mapping the new names rather than by adding instructions.

**No behaviour change on the supported path.** Output for the checked-in XED test
data is byte-identical before and after, and `x86/x86avxgen` tests pass. The
pre-existing `riscv64` objdump test failures are unrelated (they fail on a clean tree
too; they need local test data).

## Where a full regeneration still stops

    x86avxgen: generate.go:220: no zcase for "evex imm8 reg/mem opdigit"

The generate stage runs after decode and has its own gap, so even with decoding fixed
a full regeneration from current XED does not complete. Two remaining pieces of work:

1. Add the missing zcase (and whatever follows it) in `generate.go`.
2. Map the renamed APX register classes onto Go operand types, otherwise a regenerated
   table would silently lose instructions that the assembler could otherwise support.

Only then would a "regenerate the table from current XED" CL make sense, and it would
be a large diff of new instruction forms needing its own review. Neither is required
for CL 864041: the four VPDP rows are what the generator emits from VEX XED objects,
which the fixture-based run in `generator-vs-manual.diff` demonstrates.
